# Техническое задание на разработку веб-приложения «Консультант по проектам»

## 1. Общие сведения
* **Наименование проекта:** Веб-приложение «Консультант по проектам».
* **Цель:** Автоматизация генерации и первичной оценки идей по внедрению ИИ на основе анализа цифрового следа компании.
* **Целевая платформа:** «Кодекс» (среда разработки «Вайб-кодинг»).
* **Технологический стек (предполагаемый):**
  * Frontend: React / Vue.js (стандарт для «Кодекса»), TypeScript.
  * Backend: Node.js / Python (FastAPI) для оркестрации LLM и парсинга.
  * LLM: GPT-6 Sol (или актуальная на момент релиза модель OpenAI).
  * Сбор данных: Headless-браузер (Puppeteer/Playwright), библиотеки для парсинга (Beautiful Soup), API соцсетей (при наличии доступа).
* **Цветовая схема:** Светлая тема. Опорный цвет — глубокий синий (`#0A3D62`) или глубокий оранжевый (`#D35400`).

## 2. Функциональные требования

### 2.1. Экран ввода и анализа (Шаг 1)
* **Интерфейс:** 
  * Центральное текстовое поле для ввода URL (placeholder: `https://example.com`).
  * Кнопка «Проанализировать».
  * Поле URL валидируется до отправки: допускаются `http://` и `https://`; при вводе без протокола (например, `yandex.ru`) протокол `https://` подставляется автоматически.
* **Логика обработки:**
  * При клике на кнопку приложение извлекает домен, инициирует асинхронный процесс сбора данных.
  * **Сбор данных (парсинг):**
    * Главная страница и до 5 основных внутренних страниц (О компании, Услуги, Контакты, Блог).
    * Поиск в интернете по названию компании (первые 10–20 результатов выдачи).
    * Поиск официальных профилей в социальных сетях (если URL не предоставлен, но профили найдены).
* **Визуализация процесса (Progressive Disclosure):**
  * Вместо стандартного прогресс-бара — анимированный блок состояний. Каждое состояние появляется, выполняется 2–3 секунды, затем плавно заменяется следующим:
    1. «Изучаю структуру сайта...»
    2. «Читаю страницы: Главная, Услуги...»
    3. «Ищу упоминания в сети...»
    4. «Проверяю социальные сети...»
    5. «Синтезирую контекст...»
  * Блок должен быть центрирован, использовать фирменный цвет для индикатора текущего шага.

### 2.2. Экран генерации идей (Шаг 2)
* **Интерфейс:** 
  * Секция из 5 вертикальных плашек во всю ширину контейнера.
  * Каждая плашка содержит: 
    * Название проекта (жирный шрифт).
    * Описание (3–4 строки, `line-clamp: 4`).
    * Кнопка «Обсудить» (в фирменном цвете).
  * Кнопка «Перегенерировать» (под блоком плашек).
* **Логика:**
  * Генерация 5 уникальных ID проектов на основе собранного контекста. Контекст должен храниться в памяти сессии (или в `localStorage`) до закрытия вкладки.
  * При клике «Перегенерировать» — повторный вызов LLM с сохраненным контекстом, замена плашек с микро-анимации появления.

### 2.3. Модуль обсуждения и чата (Шаг 3)
* **Интерфейс (Макет с разделением экрана):**
  * **Верх:** Табы чата. При нажатии «Обсудить» на нескольких проектах открываются вкладки с названиями этих проектов. На вкладке — кнопка закрытия (крестик).
  * **Левая/правая колонка (фиксированная высота, например, 600px):** Список проектов (оставшиеся не обсужденные). Скролл запрещен, лишние проекты скрываются (или выводится уведомление).
  * **Правая/левая колонка (фиксированная высота 600px):** Окно чата. Внутренний скролл появляется при переполнении. Страница браузера не скроллируется (`body { overflow: hidden; }`).
* **Логика диалога (GPT-6 Sol):**
  * **Инициация:** При открытии таба бот приветствует: *«Вы выбрали проект [Название]. Чтобы подготовить консультацию, задам 5–7 вопросов»*.
  * **Механика вопросов:**
    * Бот выводит вопрос и под ним — плашки с вариантами ответов (если они есть).
    * **Множественный выбор:** Плашки чекбоксного типа. Пока не выбран хотя бы один вариант, кнопка «Отправить» (или «Далее») неактивна. После клика выбранные варианты подсвечиваются, появляется кнопка отправки.
    * **Единичный выбор:** Плашки радиокнопочного типа (или визуально как кнопки). При клике на один вариант ответ мгновенно улетает в чат, бот пишет следующее сообщение.
    * Пользователь может писать и свободный текст, но основной сценарий — выбор из плашек.
* **Финальная консультация:**
  * После прохождения опроса бот генерирует развернутый ответ (объемом ~0.5–1 страница).
  * **Структура ответа:**
    * Суть проекта (1 абзац).
    * Потенциальная выгода (KPI, экономия, рост выручки).
    * Оценка сроков (MVP / Full version).
    * Оценка бюджета (порядок цифр: S/M/L/XL).
    * Ключевые риски и подводные камни.
    * Что критически важно учесть при разработке.

### 2.4. Настройки и безопасность
* **Расположение:** Иконка шестерёнки в правом верхнем углу.
* **Функционал:** 
  * Всплывающее модальное окно.
  * Поле ввода «API-ключ OpenAI» (тип `password`, символы скрыты точками).
  * Кнопка «Сохранить» (ключ шифруется и сохраняется в `localStorage` или зашифрованной куке, не в открытом виде).
* **Уточнение по хранению ключа:**
  * Для демо-режима допускается хранение в `localStorage` в зашифрованном виде.
  * Для production-режима хранение ключа на клиенте запрещено: ключ хранится на backend, а клиент использует только сессионный идентификатор (`httpOnly` cookie).

## 3. Нефункциональные требования
* **Производительность:** 
  * Время отклика интерфейса на клик — не более 100 мс.
  * Таймаут сбора данных — не более 60 секунд. Если дольше — вывод ошибки «Не удалось собрать данные, проверьте URL».
* **UX/UI:** 
  * Микро-анимации появления/исчезновения текста (использовать `opacity` и `transform`, не блокировать поток).
  * Адаптивность: на мобильных устройствах список проектов уходит под чат (или чат открывается на весь экран поверх списка).
* **Обработка ошибок:** 
  * Некорректный URL, ошибка 404/403 при парсинге, пустой ответ от LLM. Ошибки должны выводиться в виде понятных тостов (уведомлений) или текста в блоке анализа, а не в консоль браузера.

## 4. Специфика реализации на «Кодексе» (вайб-кодинг)
* **Архитектура промптов:** Поскольку код пишется ИИ-инженером, ТЗ должно включать готовые промпты для генерации ключевых модулей:
  * *Промпт для парсера:* «Напиши функцию на Python, которая принимает URL, через Playwright рендерит JS, извлекает текст первых 5 ссылок навигации и возвращает JSON...»
  * *Промпт для стейта:* «Создай контекстный стор (Zustand/Pinia), который хранит: companyContext (string), ideas (array), activeChatTab (id)...»
  * *Промпт для UI:* «Сгенерируй компонент QuestionCard на React, принимающий объект {question, type: 'single'|'multi', options}, реализуй логику плашек...»
* **Ограничения среды:** Учесть лимиты «Кодекса» на длину контекста. Контекст компании должен передаваться в LLM при генерации идей и в начале каждой новой чат-сессии, но не храниться в каждом сообщении чата.

## 5. Критерии приемки (Acceptance Criteria)
1. При вводе `yandex.ru` и нажатии «Проанализировать» в течение 20 секунд последовательно отображаются 5 текстовых статусов анализа.
2. Генерируется ровно 5 плашек с непустыми названиями и описаниями.
3. При нажатии «Перегенерировать» старые плашки заменяются новыми без перезагрузки страницы.
4. В чате по клику на «Обсудить» создается новый таб. При наличии 3 табов они не ломают верстку (появляется горизонтальный скролл табов).
5. Если на вопрос с множественным выбором не выбрано ни одного варианта, кнопка отправки имеет прозрачность 0.5 и `pointer-events: none`.
6. Введенный API-ключ не отображается в открытом виде и сохраняется после обновления страницы.

## 6. Ограничения области работ (Scope)
* **Входит в MVP:**
  * Анализ одного домена за сессию.
  * Генерация 5 идей и их обсуждение в табах.
  * Ввод API-ключа и базовые настройки.
* **Не входит в MVP:**
  * Авторизация пользователей и личные кабинеты.
  * Интеграции с CRM/ERP.
  * Автопубликация отчётов во внешние системы.

## 7. API-контракты (минимально обязательные)
* `POST /api/analyze`
  * **Request:** `{ "url": "https://company.com" }`
  * **Response:** `{ "analysisId": "...", "status": "queued|running|done|error", "companyContext": "...", "sources": [{"title":"...","url":"..."}] }`
* `POST /api/ideas/generate`
  * **Request:** `{ "analysisId": "..." }`
  * **Response:** `{ "ideas": [{"id":"...","title":"...","description":"..."}] }` (ровно 5 элементов)
* `POST /api/ideas/regenerate`
  * **Request:** `{ "analysisId": "...", "excludeIdeaIds": ["..."] }`
  * **Response:** формат как у `/api/ideas/generate`
* `POST /api/chat/start`
  * **Request:** `{ "ideaId": "...", "analysisId": "..." }`
  * **Response:** `{ "chatId":"...", "greeting":"...", "questions":[...] }`
* `POST /api/chat/message`
  * **Request:** `{ "chatId":"...", "message":"...", "selectedOptions":["..."] }`
  * **Response:** `{ "assistantMessage":"...", "nextQuestion": {...} | null, "isFinal": true|false }`

## 8. Форматы данных и правила валидации
* **IdeaCard:**
  * `id` — строка UUID/slug, уникальная в рамках выдачи.
  * `title` — 8–120 символов.
  * `description` — 80–400 символов, читабельный связный текст.
* **Question:**
  * `id`, `text`, `type` (`single|multi|free`), `options[]`.
  * Для `multi` должно быть минимум 2 опции; отправка блокируется без выбранных опций.
* **FinalConsultation:**
  * Обязательные разделы: `summary`, `benefit`, `timeline`, `budget`, `risks`, `criticalPoints`.

## 9. Надежность, безопасность и эксплуатация
* **Retry-политика:** до 2 повторов при временных ошибках внешних источников (`429`, `5xx`, timeout).
* **Rate limit:** минимум 5 запусков анализа на 1 IP в минуту для защиты от перегрузки.
* **Логирование:**
  * Логировать `analysisId`, этап, длительность, итоговый статус.
  * Никогда не логировать API-ключ и полный пользовательский ввод ключей/секретов.
* **Robots/ToS:** парсер учитывает ограничения `robots.txt`; при запрете фиксирует источник как «недоступен по правилам сайта».

## 10. Расширенные критерии приемки
1. При вводе невалидного URL (`abc`, пустая строка) запрос на backend не отправляется, пользователь видит понятную ошибку в UI.
2. Если хотя бы 1 источник недоступен (403/404/timeout), анализ не падает целиком: формируется частичный контекст и предупреждение.
3. В `ideas` всегда ровно 5 уникальных `id`; дубли названий в одной выдаче недопустимы.
4. После перезагрузки страницы в рамках одной сессии доступны: последний `analysisId`, список идей и открытые чат-табы.
5. Финальная консультация содержит все 6 обязательных разделов и не короче 1200 символов.
6. На мобильной ширине (`<=768px`) чат открывается корректно, элементы управления доступны без горизонтального скролла всей страницы.
